AO3 Story Tracker

A browser extension for tracking fanfiction reading progress on Archive of Our Own.

Chrome Extension Firefox Edge Live on Chrome Web Store

The Problem

Archive of Our Own has millions of stories across thousands of fandoms, but no native way to track your reading progress across them. Readers resort to browser bookmarks, spreadsheets, or just memory — all of which break down quickly when you're juggling dozens of ongoing works.

What was missing: a lightweight, in-browser tracker that lived alongside the reading experience without requiring a separate account or app.

What I Built

A sidebar-based Chrome extension that lets you assign any AO3 story to one of six reading states, persisted locally via chrome.storage.local. The sidebar is accessible from any page on AO3 via a floating button.

The six states mirror how readers actually think about their reading queues:

For Later Reading Completed Re-reading On Hold DNF

Built for Chrome first, then ported to Firefox and Edge with a shared codebase and browser-specific manifest variants.

Key Decisions

Why a sidebar? A popup closes the moment you click away — not useful while reading. A sidebar stays open across page navigations within AO3, so you can check your list, update a status, and keep reading without losing your place.

Why six states? Most reading trackers offer three (want/reading/read). That's not enough. Re-reading is a distinct state — you've finished once and you're going again intentionally. On Hold and DNF are meaningfully different: one implies intent to return, the other doesn't. Six states covers real reading behavior without over-engineering it.

Why chrome.storage.local? No account required, no server to maintain, no privacy concerns. Data lives in the browser and stays with the user. The tradeoff is no sync across devices — a known limitation, not an oversight.

The Hardest Problem

AO3's DOM is inconsistent. The subscription button — which the extension uses to detect whether a story is tracked — renders differently depending on whether the user is subscribed or not, and the markup changed between AO3 updates without warning.

The original regex used to detect subscription state:

// original — broke on AO3's actual markup const subMatch = html.match(/name="commit"\s+value="(Subscribe|Unsubscribe)"/);

This matched the spec, not reality. AO3's actual markup had the attributes in a different order, and sometimes had additional attributes between name and value. The fix required inspecting the live DOM directly rather than relying on regex over the raw HTML string.

// fixed — query the DOM directly const btn = document.querySelector('input[name="commit"][value="Unsubscribe"]'); const isSubscribed = btn !== null;

Lesson: when scraping state from a third-party site, trust the DOM API over string matching. It's more robust to attribute reordering and whitespace variation.

What I'd Do Differently

  • Add optional cloud sync from the start — I get regular requests for cross-device support.
  • Write the DOM selectors as a separate, versioned config file so AO3 markup changes can be patched without touching core logic.
  • Build in an automated smoke test against the live AO3 DOM to catch breakage before users report it.
